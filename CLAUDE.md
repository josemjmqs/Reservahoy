# Reservahoy

Plataforma de reservas online para pequeños negocios. Cada negocio tiene una página pública (`/[slug]`) donde sus clientes reservan sin cuenta, y un panel para administrar servicios, equipo, horarios y agenda.

## Stack
- Backend: NestJS 12 (CommonJS), TypeScript, Prisma 6.19 (NO usar Prisma 7), PostgreSQL 16
- Frontend: Next.js (App Router, `src/`), TypeScript, Tailwind v4 (`@tailwindcss/postcss`)
- Node 22. Tests: Jest en modo ESM (unitarios `*.spec.ts`, integración `*.int-spec.ts` contra PostgreSQL)
- Infra: Vercel (frontend), Render (API), Neon (DB), Cloudflare (DNS, R2 para respaldos y para fotos de servicios), Resend (correo)

## Estructura
- `backend/`: API (auth, business, services, members, working-hours, time-blocks, availability, bookings, agenda, notifications, settings, storage, support, health)
- `frontend/`: Next.js. El navegador llama a `/api/*` (rewrite hacia el backend con `API_URL`), así la cookie de sesión es first-party
- `docker-compose.yml`: PostgreSQL local en el puerto 5433

## Comandos
- Todo `npm`/`npx` se ejecuta DENTRO de `backend/` o `frontend/`; en la raíz solo `docker compose` y `git`
- Backend: `npm run start:dev`, `npx nest build`, `npm test`, `npm run test:integration`
- Frontend: `npm run dev` (puerto 3001), `npx tsc --noEmit`, `npm run lint`, `npm run build`
- Base local: `docker compose up -d`; consola: `docker compose exec db psql -U reservaya -d reservaya`
- Datos de prueba: `npx prisma db seed` (en `backend/`, `prisma/seed.mts`): negocio demo `demo-peluqueria`, login de la dueña `demo@reservahoy.local` / `demo1234` y del profesional (STAFF) `diego@reservahoy.local` / `demo1234`; `SEED_TODAY=1` agrega reservas hoy. Solo corre contra bases locales. La categoría "Estilos de corte" trae tipos de corte con foto (el "Corte de pelo" genérico de Pelo lleva una descripción que remite a ella, para que no parezca repetido) (`frontend/public/seed/cortes`, fotos libres de Unsplash; créditos en `seed.mts`): la API arma la URL con `R2_PUBLIC_URL`, así que en local se ven con `R2_PUBLIC_URL=http://localhost:3001` en `backend/.env` (sin eso, y en CI, quedan sin foto). Va después de Pelo y Barba para que las e2e sigan usando "Corte de pelo" en la primera categoría. El negocio de ejemplo está en `prisma/demo-business.mts`, que comparten el seed y la demo de producción; el seed también crea esa demo (`/demo`) para probarla en local
- Demo de producción (`reservahoy.cl/demo`): un negocio con `Business.demo` y dos cuentas (dueña y profesional) sin contraseña usable. Se entra con "Ver el panel de demostración" en `/login` (`POST /auth/demo` con `role` `owner`/`staff`, límite propio de 10 por minuto, aparte del login), y la franja del panel deja cambiar de rol. Es solo lectura: `validateSession` marca la sesión con `demo` y `JwtAuthGuard` rechaza todo lo que no sea GET/HEAD/OPTIONS con 403 `DEMO_READ_ONLY` (`blockedForDemo` en `auth/session.ts`), así una ruta nueva queda bloqueada sin acordarse; cerrar sesión no pasa por el guard. Su página pública deja probar la reserva pero no la guarda (403 en `BookingsService.create`: si no, cualquiera vería en el panel demo los datos de quien reservó) y no se le mandan correos de contraseña. El slug `demo` está en `RESERVED_SLUGS`. El workflow "Demo" (`.github/workflows/demo.yml`, a diario y a mano) la vuelve a crear con `npm run demo` (`prisma/demo.mts`) contra `NEON_DATABASE_URL` para que sus reservas sigan alrededor de hoy; se detiene si el slug o los correos son de algo que no es la demo. Con los secretos `R2_IMAGES_BUCKET`, `R2_IMAGES_ACCESS_KEY_ID` y `R2_IMAGES_SECRET_ACCESS_KEY` (la clave de R2 del backend en Render, no la de los respaldos, que solo escribe en su bucket) también sube las fotos de los cortes al bucket de fotos; sin ellos ese paso se salta

## Reglas del proyecto
- El `businessId` SIEMPRE se obtiene de la membresía del usuario autenticado, nunca del cliente, con `getMembership` (`auth/membership.ts`), que solo acepta membresías activas. Recursos de otro negocio responden 404
- Roles: `OWNER` puede todo y puede haber varios (por ahora quien acepta una invitación queda como `OWNER`, un segundo dueño; más adelante el dueño elegirá qué permisos da a cada uno); `STAFF` ve y cambia solo lo suyo: su agenda (incluido cancelar), su horario sin poder cambiarlo, sus bloqueos y los de todo el negocio (no los de otros profesionales; crea y borra solo los suyos), sus ajustes, y en solo lectura servicios, equipo y datos del negocio. Una acción que no es de su rol responde 403; un recurso de otro profesional, 404. Usar `isOwner`, `assertOwner` y `scopeMemberId` (`auth/membership.ts`), nunca comparar `role === 'STAFF'` (un rol nuevo debe partir limitado). Las reglas como casos: `staff-permissions.int-spec.ts` (STAFF) e `invited-owner.int-spec.ts` (quien entró por invitación). Hoy `STAFF` solo se crea a mano (el profesional del seed y las pruebas)
- Panel según el rol: `dashboard/layout.tsx` carga `/auth/me` una vez y las pantallas lo leen con `useMe()`; qué mostrar se decide con `isOwner(me)` (`lib/me.tsx`, misma regla que el backend: nunca comparar con `'STAFF'`). El profesional ve Agenda (sin filtro de profesionales), Horario (el suyo, en solo lectura), Bloqueos (sin "Aplica a"; elimina solo los suyos) y Ajustes (sin datos del negocio); Servicios y Equipo no aparecen y sus direcciones lo llevan a la Agenda. Lo que el panel oculta lo sigue negando el backend
- Panel en celular: bajo `sm` (640 px) la navegación es una barra fija abajo con ícono por pestaña (`components/icons.tsx`, SVG propios) y desde `sm` vuelve a las pestañas de arriba; es un solo `<nav>` que cambia con CSS, nunca dos menús. Su alto es `--tabbar-h` (`globals.css`): lo que vaya fijo sobre ella (como "Guardar horario") se posiciona con esa variable. Todas las páginas declaran `viewportFit: "cover"` (`viewport` en `app/layout.tsx`): sin eso, Chrome en Android (135+, navegación por gestos) esconde al desplazar una franja de abajo y deja lo fijo con `bottom-0` tapado por la barra de gestos. Con eso `env(safe-area-inset-bottom)` cambia mientras se desplaza: lo fijo abajo lleva de relleno el máximo, `--safe-bottom-max` (`globals.css`), y solo su `bottom` sigue al valor que cambia (`bottom-[calc(env(safe-area-inset-bottom,0px)-var(--safe-bottom-max))]`). El espacio que se deja al contenido usa `--safe-bottom-max`. Nunca usar `env(safe-area-inset-bottom)` como relleno: Chrome lo detecta y la barra queda cortada mientras se ve su barra de direcciones. Los botones de uso frecuente en el celular miden al menos 40 px de alto (`h-10 … sm:h-auto`). En formularios largos, el campo que se toca sube hasta arriba para no quedar bajo el teclado: `onFocus={scrollFieldUp}` (`lib/scroll-field.ts`) en el contenedor de los campos (hoy, el de servicios). Un enlace con forma de botón usa `buttonClass` (`components/ui.tsx`), nunca un `<button>` dentro de un `<Link>`
- Celulares de todo tamaño (todo el sitio, no solo el panel): cada página cabe sin desplazamiento lateral desde 280 px (la pantalla de afuera de un plegable; Chrome en Android con la letra o la pantalla en "grande" agranda la página y la deja así de angosta). Nada de anchos fijos que no se achiquen: `max-w-full`, `min-w-0` en hijos flex y `minmax(min(Npx,100%),1fr)` en grillas; una fila de botones con `whitespace-nowrap` lleva `flex-wrap`. Todo campo donde se escribe o se elige (`input`, `select`, `textarea`) mide 16 px en toda pantalla táctil, también con el celular de lado (más ancho que `sm`) o en una tablet, y 14 px solo con mouse desde `sm` (`text-base sm:pointer-fine:text-sm`, como `fieldClass` en `ui.tsx`; nunca solo `sm:text-sm`): con menos, Safari en iPhone agranda la página al tocarlo y no la vuelve a achicar (pasó al registrarse: el panel quedó "con zoom"). Nunca `maximum-scale` ni `user-scalable=no` en el viewport para evitarlo: en Android impide agrandar con los dedos. Lo revisa `mobile-viewports.spec.ts` (Chromium y WebKit, a 280, 320, 360 y 412 px y de lado, con los diálogos). En los teléfonos reales, `OverflowWatch` (`components/OverflowWatch.tsx`, en `app/layout.tsx`, con `findOverflow` de `lib/overflow.ts`) avisa a Sentry si una página queda más ancha que la pantalla: una vez por visita para cada ruta y ancho, con la ruta sin ids (`scrubUrl`), el ancho, el navegador (`browserLabel`, solo nombre y versión) y las clases de lo que se sale, nunca texto de la página; en desarrollo también sale en la consola. Navegadores antiguos: Tailwind v4 necesita Safari 16.4 / Chrome 111; donde no funciona (iPhone que no pasa de iOS 16.3) se ve el aviso `.old-browser` de `app/layout.tsx`, con estilos en línea y sin JavaScript, que `globals.css` esconde con `@supports (color: color-mix(...))` en los demás; `OverflowWatch` también avisa a Sentry ("Navegador antiguo") si su JavaScript alcanza a correr
- Diseño visual: el skill `frontend-design:frontend-design` se usa solo para definir o renovar el sistema visual (tokens en `globals.css`, tipografía, componentes base de `components/ui.tsx`), para las páginas que ven los clientes (`/[slug]`, `/reserva/[token]`) y para pantallas nuevas sin un patrón parecido en el proyecto. El resto del panel (pantallas que se parecen a otras, cambios chicos, arreglos de comportamiento o de celular) sigue los componentes de `ui.tsx` y el patrón de las pantallas existentes, sin el skill: en el panel pesa más la consistencia que la originalidad. Con o sin el skill valen las reglas de este archivo (marca, celular, `TimePicker`, textos en español)
- La restricción `booking_no_overlap` (exclusion constraint de PostgreSQL) es la garantía final contra dobles reservas; solape y deadlock se traducen a 409
- Todas las fechas se guardan en UTC y se convierten con luxon según la zona del negocio (`America/Santiago`)
- Código y nombres en inglés; textos visibles al usuario en español
- Sesión: JWT en cookie `httpOnly` (también se acepta header Bearer para pruebas) que dura 30 días y se renueva con el uso, como mucho una vez al día (`renewSession` en `auth/session.ts`, desde `JwtAuthGuard`). El contenido del token se arma solo en `signSession` (`auth/session.ts`), que usan el login, la renovación y aceptar una invitación. El token lleva `sv` (`User.sessionVersion`): restablecer la contraseña o desactivar al miembro la incrementa y cierra las demás sesiones (`AuthService.validateSession`). En el panel, un 401 lleva a `/login?expired=1` (`lib/api.ts`)
- Quitar acceso: desactivar a un miembro (`PATCH /members/:id` con `active: false`, solo un dueño, nunca a sí mismo; también a otro dueño, así que dos dueños pueden desactivarse entre sí) cierra sus sesiones al instante y anula su invitación pendiente, en la misma transacción y solo quien lo pasa de activo a inactivo (`MembersService.revokeAccess`). Sin membresía activa el login responde 403 (`ACCESS_REVOKED`, después de validar la contraseña). La cuenta se conserva: al reactivarlo entra con la misma contraseña
- `GET /auth/me` se arma con `getMembership` y responde la cuenta con una sola `membership` (`memberId`, `role`, `displayName`, `business`); sin membresía activa, 403, y el panel cierra la sesión y lleva a `/login?revoked=1` (`dashboard/layout.tsx`)
- Correos: nunca deben romper el flujo principal (el envío captura sus errores) y se mandan sin `await` (`void`). Todos pasan por `NotificationsService.send`, que reintenta 3 veces ante fallas pasajeras (`isTransient`) con la misma clave de idempotencia de Resend; si igual no sale, avisa a Sentry (sin el destinatario)
- Errores: Sentry, solo con `SENTRY_DSN` (Render) y `NEXT_PUBLIC_SENTRY_DSN` (Vercel); sin ellas (local, CI) no envía nada. Backend: `instrument.ts` (primer import de `main.ts`) y `SentryGlobalFilter` en `AppModule`, que envía solo lo inesperado (500), no las `HttpException`. Frontend: `instrumentation-client.ts`, `instrumentation.ts` y `app/global-error.tsx`, con las opciones de `lib/sentry-options.ts`. Sentry es un tercero que ve todos los negocios: nunca le llegan datos personales. Sentry 11 recolecta todo por defecto, así que `dataCollection` va todo apagado, y `scrubEvent` (`monitoring/scrub.ts` y `lib/sentry-scrub.ts`, iguales) deja de cada petición solo método y ruta y borra correos, teléfonos, el detalle de las consultas de Prisma y los ids y tokens de las rutas (el enlace de una reserva es un id). Un `catch` que se traga un error que importa (como los avisos por correo) llama a `Sentry.captureException`. Cada error lleva el commit desplegado como `release` (`RENDER_GIT_COMMIT` en el backend; en el frontend `VERCEL_GIT_COMMIT_SHA`, que `next.config.ts` pasa a `NEXT_PUBLIC_SENTRY_RELEASE` al compilar). Con release Sentry también manda "sesiones" (una por visita en el navegador, la vida del proceso y un resumen de peticiones por minuto en los servidores): van apagadas (`BrowserSession`, `ProcessSession` y `httpIntegration({ sessions: false })`), porque solo se envían errores (y los avisos de `OverflowWatch`, `captureMessage` una vez por visita). Sin trazas de rendimiento ni grabación de sesiones
- Al crear una reserva se avisa por correo a los miembros activos y con cuenta según `Member.newBookingsScope` (`BookingsService.notifyStaff`, preferencia `newBookings` en `/settings`): `ALL` todas las del negocio (solo vale para un dueño; un profesional que la pide recibe 403), `OWN` solo las que atiende, `NONE` ninguna. Un profesional no recibe datos de clientes de otros. Parte en `OWN` (como un rol nuevo); el registro y aceptar una invitación dejan al dueño en `ALL`. En Ajustes, un dueño sin otros miembros activos (`GET /members`) elige solo "Recibir" o "No recibir": "Recibir" guarda `ALL` (al sumar a alguien sigue recibiendo todas) y aparece marcado con `ALL` u `OWN`; con equipo vuelven las tres opciones
- Si el negocio cancela (el dueño, o el profesional en una reserva suya: `PATCH /agenda/:id/status` a `CANCELLED`, motivo opcional `reason`), se avisa al cliente por correo una sola vez: solo quien pasa la reserva de activa a cancelada envía (`updateMany` condicional en `AgendaService.updateStatus`)
- Servicio listo: marcar una reserva `COMPLETED` siempre le avisa al cliente por correo que su servicio está listo (pensado para negocios donde el cliente deja algo y vuelve a buscarlo, pero vale para todos; no es un ajuste: no hay casilla en Ajustes ni campo en `PATCH /business`), una sola vez: igual que al cancelar, solo quien la pasa a completada envía, desde activa o desde "No se presentó" (`COMPLETABLE` en `agenda.service.ts`, `canComplete` en `lib/types.ts`: puede haberse marcado por error y el cliente sí vino; esa tarjeta deja solo "Completada"). En la Agenda, "Completada" abre siempre un diálogo (`CompleteBookingDialog`) que dice que se le escribirá al cliente y deja sumar hasta 4 fotos (`MAX_COMPLETED_PHOTOS`), que se envían con `POST /agenda/:id/complete` (campo `photos`, reducidas en el navegador, tipo validado por los bytes) y van dentro del correo como imágenes en línea (`cid:`). Las fotos no se guardan en R2: el bucket es público y son cosas del cliente. Hasta enviarlas quedan como borrador de la reserva solo en ese navegador (`lib/photo-drafts.ts`, IndexedDB, ya reducidas): se puede cerrar el diálogo o recargar y volver a sumar otra, y la tarjeta de la Agenda muestra "N fotos guardadas, sin enviar". Se borran al enviar, a los 7 días, cuando la reserva ya no se puede completar (`syncDrafts`, al cargar la Agenda) y al cerrar sesión, al quitarse el acceso o al vencer la sesión (`clearDrafts`: pueden quedar en un equipo compartido). Si IndexedDB falla, el diálogo funciona sin recordar las fotos. Esa ruta responde `notified` (si se le escribió: no, si la reserva ya estaba completada o cancelada). `PATCH /agenda/:id/status` a `COMPLETED` también avisa (sin fotos)
- Datos del negocio (nombre, teléfono, dirección `address`, color de marca `brandColor` en `#rrggbb`): `GET/PATCH /business`, solo el `OWNER` los cambia. En Ajustes el color se elige entre los sugeridos o con "Otro color", que abre `ColorPicker` (`components/ColorPicker.tsx`): un panel propio como el `TimePicker` con tono, saturación y brillo; nunca `<input type="color">` (la paleta del sistema parte en una grilla de colores fijos). El código `#rrggbb` queda escondido en "Ya tengo el código de mi color"; antes de subirlo, el logo se encuadra en `LogoCropper` (`components/LogoCropper.tsx`, un `<dialog>` como el `ColorPicker`): se ve el círculo de la página pública, se arrastra la imagen (o con las flechas), se cambia su tamaño con la barra o pellizcando, y "Así se verá en tu página" lo muestra a 64 px sobre el color del formulario (aunque no esté guardado); tocar fuera no lo cierra, para no perder el encuadre. Se recorta en el navegador a un cuadrado de 512 px (lo que se sube es lo que se vio; lo revisa `business-branding.spec.ts`), y se sube y se quita con `POST/DELETE /business/logo` (campo `logo`, solo el `OWNER`: el rol se revisa antes que R2). `GET /public/:slug` también trae `address`, `brandColor`, `logoUrl` y `todayHours` (`AvailabilityService.todayHours`: hoy, en la zona del negocio, de la primera apertura al último cierre de los profesionales que atienden; no cuenta a quien tiene un bloqueo, suyo o de todo el negocio, que cubre todo su horario de hoy; `null` si nadie atiende; el almuerzo no corta el rango). Las preferencias de cada miembro van en `/settings`
- Dirección: se guarda solo el texto (una línea) y el enlace a Google Maps se arma con `mapsUrl` (búsqueda sin clave; está en `notifications.service.ts` y en `frontend/src/lib/maps.ts`, iguales). Sale en la página pública, en la de la reserva (`/reserva/[token]`) y en el correo de confirmación
- Color de marca en la página pública: `brandStyle` (`lib/brand.ts`) define `--brand` y `--brand-fg` en el `<main>` y las clases `bg-brand`, `text-brand-fg`, `border-brand`, `hover:bg-brand-hover` (`globals.css`) los usan; sin color, el índigo del logo (`DEFAULT_BRAND`, `#4f39f6`). El encabezado es una franja con el color del negocio (de borde a borde en el celular, una tarjeta desde `sm`) con el logo en un círculo recortado (`rounded-full object-cover`, como la foto de perfil de Instagram, para que el negocio use la misma; la vista previa de Ajustes también es circular: `PhotoPicker` con `round`; sin logo no se muestra nada en su lugar, ni iniciales), el nombre, "Hoy atiende de … a …" (`todayHours`, con `time`) y el teléfono y la dirección como enlaces (el teléfono abre WhatsApp si es un celular, `whatsappUrl` en `lib/whatsapp.ts`: sin código de país se asume Chile, y un fijo chileno, que no tiene WhatsApp, llama con `tel:`; lo mismo en la página de la reserva, con `PhoneLink` de `components/PhoneLink.tsx`, y en los correos al cliente con "Si tienes dudas", con la copia de `whatsappUrl` en `notifications.service.ts`); la confirmación es un comprobante con el día y la hora grandes sobre el mismo color. La grilla de días son dos filas de 7 sin desplazamiento lateral (con mouse no se descubre), con el mes arriba y "Hoy" en el primero; "Otra fecha" es el `<input type="date">` que usan las pruebas e2e para fechas lejanas. El texto encima es blanco si contrasta 4,5:1 y si no el que contraste más (`textOn`). Bordes y marcas de lo elegido sobre fondo claro usan `--brand-ring` (`border-brand-ring`, `outline-brand-ring`; en valores arbitrarios `var(--brand-ring)`, porque `--color-brand-*` se resuelve en `:root`): el color de marca, oscurecido si no contrasta 3:1 con el blanco (`ringOn`)
- Sistema visual ("la hora manda", en `globals.css`): una sola familia, Instrument Sans (`app/layout.tsx`, con el eje de ancho). Toda hora que se muestre o se elija usa la utilidad `time` (angosta, seminegrita, cifras de igual ancho): es lo que distingue a Reservahoy. Neutros con un leve tinte índigo que reemplazan la escala `gray` de Tailwind (las pantallas existentes la usan tal cual); en código nuevo, los nombres con significado `ink`, `muted`, `line`, `paper` y `accent` (`accent-hover`, `accent-soft`). El índigo del logo (`#4F39F6`) solo para acciones y lo elegido. Bordes por jerarquía: `rounded-control` (botones y campos), `rounded-card` (tarjetas), `rounded-sheet` (diálogos y paneles). Sombra solo en lo que flota (`shadow-float`); las tarjetas van con borde y sin sombra. Un nombre nuevo del sistema se agrega también a `extendTailwindMerge` en `ui.tsx`. Las fechas largas ("Sábado, 9 de enero") llevan mayúscula solo al inicio con `capitalize` de `lib/format.ts`, nunca con la clase `capitalize` de CSS, que la pone en cada palabra ("9 De Enero")
- Correo de contacto público: `contacto@reservahoy.cl` (`CONTACT_EMAIL`, `frontend/src/lib/contact.ts`), en términos, privacidad y el pie de la portada. Es una regla de Cloudflare Email Routing que reenvía a la casilla del dueño: no guarda correos, solo recibe, y el catch-all queda apagado. Nunca poner un correo personal en el sitio
- Privacidad y términos (`/privacidad`, `/terminos`, Ley 21.719): para los datos de los clientes el negocio es el responsable y Reservahoy el encargado (el acuerdo de encargo está en los términos); para las cuentas del panel y los mensajes de ayuda, Reservahoy es el responsable. Quien opera Reservahoy es `OPERATOR_NAME` (`lib/contact.ts`). Lo que prometen es un compromiso: al cerrar un negocio se borra todo en 30 días (y de los respaldos en 30 más), se responde en 30 días corridos y se avisa por correo a los negocios antes de sumar un proveedor que reciba datos de clientes. Un dato nuevo que se guarde, un proveedor nuevo o un cambio en esos plazos actualiza las dos páginas y su fecha
- Precio (portada `#precio` y `/terminos#precio`): hoy es gratis, y los negocios creados antes del día en que se anuncie el cobro son "fundadores": nunca pagan por las funciones que existan ese día, mientras su cuenta siga abierta; el cobro se anuncia por correo a todos con 30 días de anticipación y solo aplica a los negocios nuevos, y una función de pago agregada después la contratan si quieren. Es un compromiso: quién es fundador se sabe por `Business.createdAt` frente a la fecha del anuncio (no hay campo aparte); al implementar cobros, nunca cobrar a un negocio fundador por lo que ya tenía
- Ayuda y sugerencias: cualquier miembro activo (dueño o profesional) le escribe al equipo de Reservahoy desde `/dashboard/support` (ícono "?" del encabezado, fuera de las pestañas, y "Escribirnos" en Ajustes): reportar un problema, sugerir una mejora o una duda (`kind`), mensaje de 10 a 2000 caracteres y la pantalla desde donde llegó (`?from=`, solo rutas `/dashboard...`). `POST /support` lo guarda en `SupportRequest` (con negocio, miembro y navegador) y avisa por correo a `SUPPORT_EMAIL` con `replyTo` del usuario, para responderle directo; sin esa variable solo queda en la base. Máximo 5 por hora por miembro (`SUPPORT_MAX_PER_HOUR`, 429). No hay pantalla para leerlos: el correo o la consola de la base
- Los correos se normalizan a minúsculas (trim + lowercase)
- Un negocio recibe reservas solo si tiene un dueño activo con `emailVerifiedAt` (`AvailabilityService.acceptsBookings`)
- Los tokens de un solo uso (reset de contraseña, verificación de correo, invitaciones) se guardan solo como hash SHA-256 (las invitaciones usan `newToken`/`hashToken` de `auth/one-time-token.ts`)
- Invitaciones: solo un dueño con el correo verificado (si no, 403) invita por correo a un profesional activo y sin cuenta (`POST/DELETE /members/:id/invitation`). Un correo que ya tiene cuenta no se invita (409): una persona pertenece a un solo negocio. El enlace (`/invitacion/[token]`) vale 7 días, máximo 3 por hora por miembro, y reenviar anula la anterior. Aceptar (`POST /invitations/:token/accept`, público) crea la cuenta con el correo verificado, la enlaza al miembro como `OWNER` y deja la sesión iniciada, todo en una transacción (`InvitationsService.accept`); el `displayName` público no cambia. `GET /members` trae `account` (`active`/`invited`/`none`) y el correo invitado solo para el dueño. Como el invitado entra verificado y como dueño, un dueño sin verificar no puede invitar: si no, el invitado habilitaría las reservas por él. En Equipo se puede desactivar a cualquiera menos a uno mismo ("(tú)"), y desactivar pide confirmación (activar no)
- Al crear una ruta nueva en el frontend, agregarla a `RESERVED_SLUGS` (`register.dto.ts`)
- Un servicio nuevo queda asignado solo al dueño que lo crea (`ServicesService.create`); los demás se suman desde Equipo
- Una reserva tiene uno o más servicios en `BookingItem` (orden en `position`) y los hace un solo profesional seguidos: el bloque dura la suma (`blockFor`). Usar `AvailabilityService.resolveServices` y `membersForServices`; máximo en `MAX_SERVICES_PER_BOOKING`
- Horario: una fila por día (`WorkingHours`) con almuerzo opcional (`breakStartsAt`/`breakEndsAt`, los dos o ninguno, estrictamente dentro del horario: `dayHoursError` en el DTO, con la misma regla en `dayError` de `lib/hours.ts`, que usa `dashboard/hours/page.tsx`). En el panel las horas (del horario y de los bloqueos) se eligen con `TimePicker` (`components/TimePicker.tsx`): un panel propio (`<dialog>`, desde abajo en el celular y centrado desde `sm`) con las 24 horas y después los minutos de 5 en 5 (`MINUTE_STEP`), en formato 24 h. Nunca `<input type="time">`: en Android abre el reloj del sistema, que muestra "6:00 p. m." según el idioma del teléfono y en pantallas angostas corta "Establecer". El panel se monta solo mientras está abierto; en e2e se usa `pickTime` (`e2e/helpers.ts`). La API y el panel aceptan cualquier minuto (una hora guardada como 10:07 se ve y se guarda igual). "Copiar a los días marcados" (en el lunes) pone su horario y almuerzo solo en los días con el check; los desmarcados siguen cerrados; la API acepta cualquier minuto. `computeSlots` arma la mañana y la tarde por separado (`workingSpans`): ninguna hora, ni el bloque completo de varios servicios, cruza el almuerzo, y la tarde parte justo al terminar
- Fotos y logo: se guarda solo `imageKey` / `logoKey` (ruta en el bucket) y la API responde `imageUrl` / `logoUrl` armada con `R2_PUBLIC_URL` (`StorageService.urlFor`). El tipo se valida por los bytes (`detectImageType`), nunca por el nombre o el Content-Type. Sin variables `R2_*` la subida responde 503

## Flujo de trabajo
- Una rama por función (`feat/...`, `fix/...`, `docs/...`), PR, CI en verde (`backend`, `frontend`, `integration`, `e2e`) y merge
- Los PR se mergean apenas el CI está en verde, con el merge automático de GitHub (mergear a `main` despliega a producción, y Reservahoy ya tiene usuarios reales). La excepción la decide el dueño: cuando dice que un cambio no se debe mergear solo, ese PR se abre sin `--auto` y lo mergea él tras revisarlo
- Push y PR desde la carpeta local con la sesión de GitHub CLI del dueño (`gh auth login` + `gh auth setup-git`): `git push -u origin <rama>`, `gh pr create` y, enseguida (salvo que el dueño haya dicho que ese cambio no), `gh pr merge <n> --auto --merge`. GitHub mergea solo cuando pasan los checks obligatorios y borra la rama remota (el repo tiene "Allow auto-merge" y "Automatically delete head branches"). Si se suben más commits al PR, el merge automático sigue activo. Si `gh` no está en el PATH, usar `C:\Program Files\GitHub CLI\gh.exe`. Nunca pedir ni manejar tokens: si la sesión vence, el dueño corre `gh auth login`
- `main` está protegida por un ruleset: solo se cambia por PR, exige `backend`, `frontend`, `integration` y `e2e` en verde y la rama al día con `main` (si quedó atrás: `gh pr update-branch <n>`). Si un check falla, el merge automático espera: arreglar en la misma rama y subir otro commit. Un job de CI nuevo que deba bloquear el merge se agrega también al ruleset
- Para volver a `main` tras un merge usar `git switch -C main origin/main`, nunca `git checkout main` con un `main` local desactualizado
- Tras mergear, borrar la rama y crear una nueva para el siguiente cambio
- Antes de commitear: `npx nest build` (backend) y `npx tsc --noEmit` + `npm run lint` + `npm run build` (frontend)
- En efectos de React no llamar `setState` de forma síncrona: el efecto llama a una función que solo hace el fetch y guarda el resultado en el `.then` (regla de `eslint-config-next`)
- Cambios de interfaz: antes de mergear, levantar backend y frontend con el seed e iniciar sesión con Playwright para revisarlos en pantalla (escritorio y celular)
- Commits pequeños con prefijos `feat:`, `fix:`, `docs:`, `chore:`, `test:`
- Tras cada cambio, anotar en `CODE_REVIEW.md` los archivos modificados en orden de lectura, agrupados por commit (hash + mensaje). Es una lista local (en `.gitignore`): el dueño lo lee de arriba hacia abajo y borra lo que ya revisó, así que las entradas nuevas van SIEMPRE al final y nunca se restauran las borradas
